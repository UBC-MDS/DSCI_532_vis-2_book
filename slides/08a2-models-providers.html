Models vs Platforms/Providers

Models vs Developers vs Providers

  • Model — the trained neural network itself (GPT-4.1, Claude Sonnet 4.6, Llama 3.3 70B)
  • Developer — the lab that trains and releases the model (OpenAI → GPT-4.1, Anthropic → Claude, Meta → Llama, Alibaba → Qwen)
  • Provider / platform — hosts and serves models via API (OpenAI, Anthropic, GitHub Models, Groq, Azure)
  • Developer = provider for proprietary models (OpenAI both trains and serves GPT-4.1)
  • Developer ≠ provider for open models (Meta trains Llama → Groq, AWS, Azure serve it)

In chatlas, switching providers means changing one constructor:

from chatlas import ChatOpenAI, ChatAnthropic, ChatGithub, ChatGroq

chat = ChatGithub(model="gpt-4.1-mini")      # free, 8k input cap
chat = ChatOpenAI(model="gpt-4.1-mini")      # paid, full 1M context
chat = ChatAnthropic(model="claude-sonnet-4-6-20250514")  # paid, 200k (1M beta)
chat = ChatGroq(model="llama-3.3-70b-versatile")          # free, 128k context

Key point: the model is the same GPT-4.1-mini whether you access it through GitHub Models or OpenAI directly. What changes is the limits and pricing the provider imposes. The Chat* constructor names refer to the provider, not the developer. For Anthropic and OpenAI these happen to be the same company; for GitHub Models they’re different.

Context Window vs Provider Input Limit

Context window = total token budget for one API call (input + output).

  • GPT-4.1 family: 1M context, 32k max output
  • Claude 4.6 (Sonnet/Opus): 200k standard, 1M beta
  • Llama 3.3 70B: 128k context

But providers can cap it lower:

  • GitHub Models limits GPT-4.1-mini to 8k input — that’s 0.8% of the model’s 1M capacity!
  • Same model, same weights, vastly different limits

Effective max input ≈ context window − max output tokens. A “1M context” model with 32k max output → ~968k usable input.

GitHub Models is a playground: the 8k input cap is a huge difference from the model’s 1M context. We will hit this limit when sending PDFs or long conversations. The 150 req/day cap also means querychat can burn through the budget in a single session.

Pricing Deep Dive

Output tokens cost 2-5x more than input tokens. Why? Reading is cheap (and sometimes parallelizable); generating is expensive.
